# Backend README

This document covers how to run the backend API and the currently active agent workers.

## Prerequisites

- Python 3.12+
- Poetry
- Redis reachable via `REDIS_URL`
- Environment variables configured in your `.env`

Install dependencies:

```bash
poetry install
```

## API entrypoint

Main app:
- Module: `dermascan/backend/app/main.py`
- Object: `app`

Run the backend API on port `8087`:

```bash
poetry run uvicorn dermascan.backend.app.main:app --host 0.0.0.0 --port 8087 --reload
```

Health check:

- `GET /health`

Versioned routes are under `/v1`.

## Active endpoints

- `POST /v1/orchestrator/requests`

## Webhook payload contract (WhatsApp + Telegram)

This section explains what your webhook payload must contain so the backend can normalize it and enqueue it to Redis (`orchestrator:jobs`).

### Redis fields written by both webhooks

Each accepted webhook message is normalized and pushed with:

- `request_id`: generated by backend (new UUID per inbound message)
- `case_id`: conversation scope used by downstream workers
- `client_id`: end-user identity
- `message_id`: source platform message id
- `channel`: `"whatsapp"` or `"telegram"`
- `payload`: normalized JSON string with:
  - `content.text`
  - `content.attachments[]`

Telegram also includes:

- `username`: from Telegram sender when available

### WhatsApp payload requirements (`POST /v1/webhooks/whatsapp`)

Expected message location:

- `entry[].changes[].value.message` (or legacy `value.messages[0]`)

Minimum required fields inside the message:

- `from` → used as `client_id`
- `id` → used as `message_id`

Common supported content:

- Text: `text.body`
- Image/document message types: `type` with `image` or `document`
- Optional attachment list: `attachments[]`
  - Supports `base64` / `data_base64` / `image_base64`
  - Or `media_ref` / `blob_ref`
  - Or fallback IDs like `media_id`

Normalization notes:

- `case_id` is set to `client_id` for WhatsApp.
- Empty/invalid messages are ignored (not enqueued).

### Telegram payload requirements (`POST /v1/webhooks/telegram`)

Expected message location:

- `message` (or `edited_message`)

Minimum required fields:

- `chat.id` → used as `conversation_id` and `case_id`
- `from.id` (fallback to `chat.id`) → used as `client_id`
- `message_id` → used as `message_id`

Common supported content:

- Text: `text`
- Caption: `caption`
- Photos: `photo[]` (backend downloads the largest image via Telegram API, stores it, then writes as attachment)

Normalization notes:

- `username` is captured from `from.username` when present.
- Empty/invalid messages are ignored (not enqueued).

### Practical guidance for WhatsApp API implementers

- Always send stable sender identity in `from` and stable platform message ID in `id`.
- Include message body in `text.body` for text messages.
- For images, prefer either a valid base64 payload or a resolvable `media_ref`/`blob_ref`.
- Keep payload shape consistent across all events to avoid messages being ignored during normalization.

## Start agent workers (for now)

Run each worker in its own terminal from the repository root.

### 1) Orchestrator worker

File: `dermascan/backend/services/agents/orchestrator_worker.py`

```bash
poetry run python dermascan/backend/services/agents/orchestrator_worker.py
```

What it does:
- Consumes orchestrator job and signal streams.
- Invokes the orchestrator agent.
- Enqueues outbound messages.

### 2) Diagnose worker

File: `dermascan/backend/services/agents/diagnose_worker.py`

```bash
poetry run python dermascan/backend/services/agents/diagnose_worker.py
```

What it does:
- Consumes `diagnose:jobs` from Redis.
- Resolves image input payloads.
- Calls the MedGemma gateway and emits status events.

## Suggested local run order

1. Start Redis.
2. Start MedGemma gateway/API (if diagnose flow is required).
3. Start backend API (`8087`).
4. Start `orchestrator_worker.py`.
5. Start `diagnose_worker.py`.
